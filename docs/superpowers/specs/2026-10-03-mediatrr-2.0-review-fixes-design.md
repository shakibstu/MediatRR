# MediatRR 2.0 review fixes design

Date: 2026-10-03
Baseline: `origin/master` d463bba (identical to the published 1.3.0 package)
Branch: `fix/review-findings-2.0.0`

## Goals

Fix the defects found in the 2026-10-03 review of MediatRR 1.3.0 without changing the target framework or the public programming model.

1. A notification handler runs inside a DI scope that lives until the handler finishes.
2. Retry is per handler and in place: a failing handler never re-runs its siblings, and each handler has its own attempt budget.
3. No single message can stop the worker; shutdown always completes and honours the host's cancellation token.
4. Every failed or abandoned notification ends in the dead-letter queue with its message, its real exception and a correct attempt count.
5. The bounded channel exerts backpressure; nothing is dead-lettered merely for waiting.
6. Dispatch works for explicit interface implementations and multi-interface handlers, and exceptions keep their type.
7. The registration API cannot be misused into a host that fails to start.
8. The source generator emits compilable, complete registrations and never breaks a consumer that does not use it.
9. The runtime assembly carries no Roslyn reference; the package depends only on abstraction packages.

## Non-goals

- Changing the target framework. MediatRR, MediatRR.Contract and the new MediatRR.Generators all stay netstandard2.0.
- Sharing the caller's DI scope with handlers. Isolated per-call scopes stay and are documented as such.
- Renaming `Void`, changing the contract interfaces, or adding base-type (polymorphic) notification dispatch.
- A separate NuGet package for the generator. It ships inside the MediatRR package.

## Decisions

| Topic | Decision |
|---|---|
| Scope model | Isolated per-call async scopes (`CreateAsyncScope` plus `await using`). README corrected. |
| Version | 2.0.0. The configuration-object overload disappears from the public surface, retry and dead-letter semantics change, and the generator moves to its own assembly. |
| Dependencies | `Microsoft.Extensions.Hosting.Abstractions`, `Microsoft.Extensions.DependencyInjection.Abstractions` and `System.Threading.Channels`, each with an 8.0.x minimum. Test projects stay on 10.0.9. |
| Worker model | Single reader. A concurrency slot is acquired per handler before that handler starts, the reader waits for slots, and a per-message task owns the scope. |
| Concurrency meaning | `MaxConcurrentMessageConsumer` keeps its current meaning: the maximum number of handler pipelines running at once. |
| Commit format | Plain descriptive messages, no ticket prefix, matching the repository history. |

## Architecture

### Worker

`HandleNotificationsWorker` keeps one reader loop in `ExecuteAsync`. For each message it starts a per-message task that:

1. Creates an async scope from `IServiceScopeFactory`.
2. Asks the notification wrapper for one delegate per registered handler, with the `INotificationHandlerBehavior` pipeline already composed around the handler call. Each delegate takes a `CancellationToken` and returns a `Task`.
3. For each delegate, awaits a semaphore slot and then starts a handler task that runs the delegate with in-place retry.
4. Signals "all handlers started" back to the reader, awaits all handler tasks, and disposes the scope.

The reader awaits the "all handlers started" signal before reading the next message. When every slot is busy the reader stops reading, the bounded channel fills, and `Publish` blocks exactly as `NotificationChannelSize` promises. The one-minute semaphore timeout, the `semaphoreAcquired` flag, the Guid-keyed task dictionary and the `ContinueWith` bookkeeping are removed. The reader keeps the set of per-message tasks only so that shutdown can await them.

Resolving handlers, building pipelines and starting them all happen inside the per-message task's try/catch. A handler with a missing dependency or a behavior that throws synchronously dead-letters that message and the reader continues. `ExecuteAsync` cannot fault because of message content.

### Retry

Retry happens inside the handler task and never re-enqueues. Attempt 1 runs the delegate. Cancellation means an `OperationCanceledException` observed while the worker's stopping token is cancelled; any other exception, including an `OperationCanceledException` raised by a handler's own token, is a failure. On a failure, if the number of retries made is below `MaxRetryAttempts`, the task releases its slot, waits `DelayBetweenRetries`, re-acquires a slot and runs the same delegate again. When retries are exhausted it dead-letters with the last exception. Each handler owns its attempt counter, so a sibling that already succeeded is never re-run, and two failing handlers produce exactly one dead letter each. `NotificationPublishContext` shrinks to the message and its runtime type.

A behavior exception takes the same path as a handler exception: it is retried under the same policy and dead-lettered with the message.

### Dead letters

One private helper writes every entry as `DeadLettersInfo(message, exception, attemptCount, DateTime.UtcNow)`. `AttemptCount` is the total number of attempts made, as its documentation says; with two retries a permanently failing handler records 3. No entry is ever written with a null message.

### Shutdown

`StopAsync(cancellationToken)`:

1. Completes the channel writer so no new message is accepted.
2. Awaits the drain (the reader loop plus all in-flight per-message tasks) raced against `cancellationToken`.
3. Calls `base.StopAsync(cancellationToken)`, which cancels the stopping token handed to handlers.
4. Dead-letters anything abandoned: handler tasks that ended with `OperationCanceledException` and items still unread in the channel, each with the message and an `OperationCanceledException`.

The drain is bounded by the host's shutdown timeout. A handler that ignores its token can delay shutdown only until that timeout fires.

`Publish` after the writer is completed throws `InvalidOperationException` with the message "MediatRR notification processing has stopped; notifications can no longer be published." instead of a bare `ChannelClosedException`.

### Dispatch

`HandlerCache` is deleted. Three internal closed-generic wrappers replace it, each created once per runtime message type with `MakeGenericType` plus `Activator.CreateInstance` and cached in a static `ConcurrentDictionary<Type, ...>`:

- `RequestHandlerWrapper<TRequest, TResponse>`: resolves `IEnumerable<IPipelineBehavior<TRequest, TResponse>>` and `IRequestHandler<TRequest, TResponse>`, composes the pipeline, calls `Handle` directly.
- `StreamRequestHandlerWrapper<TRequest, TResponse>`: the same for `IStreamBehavior` and `IStreamRequestHandler`.
- `NotificationWrapper<TNotification>`: runs the publish-time `INotificationBehavior<TNotification>` pipeline around the enqueue, and builds the per-handler delegates for the worker from `IEnumerable<INotificationHandler<TNotification>>` and `IEnumerable<INotificationHandlerBehavior<TNotification>>`.

Because the wrappers call interface methods, explicit interface implementations work, classes implementing two handler interfaces work, and a synchronous throw reaches the caller or the dead-letter queue with its original type. A missing handler still throws `InvalidOperationException("No handler registered for {type}.")`.

### Mediator

Every scope is `scopeFactory.CreateAsyncScope()` consumed with `await using`, including inside the `CreateStream` async iterator. `Publish` asks `IServiceProviderIsService.IsService(typeof(INotificationHandler<T>))` when the container provides that service and otherwise always enqueues; the worker's "no handlers" check remains the authority. `Publish` never constructs a handler.

### Registration API

- `AddMediatRR(IServiceCollection, Action<MediatRRConfiguration>, ConcurrentQueue<DeadLettersInfo>)` is the only public entry point. The overload taking a `MediatRRConfiguration` becomes private.
- Registrations use `TryAddTransient`, `TryAddSingleton` and `AddHostedService`, so a second call is a no-op.
- `AddMediatRR` throws `ArgumentOutOfRangeException` when `NotificationChannelSize` or `MaxConcurrentMessageConsumer` is below 1.
- `AddNotificationHandler` registers a policy only when one is passed. A passed policy must have `MaxRetryAttempts >= 0` and `DelayBetweenRetries >= TimeSpan.Zero`, otherwise `ArgumentOutOfRangeException`.
- The duplicated defaults in the extension are removed; `MediatRRConfiguration` is the single source of defaults.

### Source generator

A new project `src/MediatRR.Generators` (netstandard2.0, `IsRoslynComponent`, `Microsoft.CodeAnalysis.CSharp` 4.3.1, `Microsoft.CodeAnalysis.Analyzers`, `EnforceExtendedAnalyzerRules`) contains one `HandlerRegistrationGenerator`:

- Predicate: `TypeDeclarationSyntax` that is a class or record declaration with a non-null base list.
- Transform: resolve the symbol; skip abstract, static, generic and non-accessible types (the type and every containing type must be public or internal); for every interface in `AllInterfaces` whose `OriginalDefinition` is `IRequestHandler<,>` or `IStreamRequestHandler<,>`, produce a registration record (interface display string, implementation display string, kind) using `SymbolDisplayFormat.FullyQualifiedFormat`.
- Pipeline: `Where(not null)`, `SelectMany`, `Collect`, one `RegisterSourceOutput`.
- Output: one file, `MediatRR.ServiceGenerator.g.cs`, with an auto-generated header, a block-scoped namespace `MediatRR.ServiceGenerator`, and an `internal static class SourceGeneratorInjectDependencies` exposing `AutoRegisterRequestHandlers(this IServiceCollection)` and `AutoRegisterStreamHandlers(this IServiceCollection)`. Both methods always exist, even with no registrations. The output uses only C# 7.3 syntax.

The two existing generator files are deleted from the runtime project.

- `.github/workflows/ci.yml`: install only the 10.0.x SDK.

### Documentation

README changes: notifications require a running host or a manually started hosted service, with a generic-host example; handlers never share the caller's scope; retry is per handler and in place; `AttemptCount` is total attempts; omitting a policy means no opinion; auto-registration supports non-abstract, non-generic, accessible classes and records and registers every handler interface; `Publish` after shutdown throws `InvalidOperationException`; configuration values are validated. The notification examples in `tests/MediatRR.Documentation.Examples` use `Host.CreateApplicationBuilder` and stop the host instead of sleeping.

## Behavior changes visible to consumers

| Area | 1.3.0 | 2.0.0 |
|---|---|---|
| `AddMediatRR(MediatRRConfiguration)` | public, cannot start a host | private |
| Retry | re-runs every handler of the message | re-runs only the failing handler |
| `AttemptCount` | retries made | total attempts made |
| Behavior failure | dead letter with null message, no retry | retried, dead letter with message |
| Backpressure | none; 60 s wait becomes a dead letter | `Publish` blocks when channel and slots are full |
| `Publish` after stop | `ChannelClosedException` | `InvalidOperationException` |
| Omitted retry policy | explicit default, conflicts with an explicit one | no opinion |
| Invalid configuration | silently accepted or late failure | `ArgumentOutOfRangeException` from `AddMediatRR` |
| Generated code | requires C# 10 | C# 7.3 |
| Package dependencies | `Microsoft.Extensions.Hosting` 10.0.9 | abstraction packages 8.0.x |
